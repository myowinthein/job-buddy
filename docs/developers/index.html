For developers

A browser extension.
A local profile.
No backend to run.

Job Buddy is a single-package Chrome MV3 extension. Start it with WXT, work with synthetic data, and test real form writes in an isolated browser.

Open the repositoryRead the user walkthrough

The UI uses React 19, TypeScript 5.9 and Tailwind CSS v4. WXT 0.20.26 owns extension builds and development. Vitest 4 covers domain behavior; Playwright checks actual browser interaction. Profile data lives in chrome.storage.local.

Use Node.js 22 from .nvmrc and pnpm 11.7.0 from package.json. 

git clone https://github.com/myowinthein/job-buddy.git
cd job-buddy
nvm use
corepack enable
pnpm install
pnpm dev

pnpm install also runs wxt prepare to generate extension types. pnpm dev starts the server at 127.0.0.1:3000 by default and normally opens a development browser with the extension loaded.

Use your regular Chrome when you need to

The auto-opened development browser is convenient for most UI and form work. Google authentication may be restricted in an automated Chromium session. To test real Drive sign-in, load the development build in regular Chrome:

  1. Keep pnpm dev running.
  2. Open chrome://extensions/ and enable Developer mode.
  3. Select Load unpacked and choose .output/chrome-mv3-dev/.
  4. Use that extension’s own Settings to configure your key and Drive connection.

The development logo is amber; production is blue. Restart WXT after adding an HTML entrypoint. Reload the extension and refresh an already-open job form when a content-script change has not reached it.

Configuration

Add only the integrations you need

There is no database, server deployment or environment file required to edit profile UI. A Gemini key saved in Settings enables autofill, resume import and AI mapping review. Drive needs a build-time OAuth client ID. 

cp .env.example .env.development
cp .env.example .env.production

Edit those local, ignored files yourself. Never commit real values. They are separate so development and production can use different extension redirect IDs.

Entry Where and why
VITE_GOOGLE_DRIVE_CLIENT_ID Web application OAuth client ID for Drive. Use separate dev/prod clients. The extension embeds the client ID, not a client secret.
VITE_GEMINI_API_KEY Optional development-only fallback. Put it in .env.development; production ignores it. An explicitly removed key or reset suppresses seeding until a key is saved again.

Set up Google Drive OAuth

  1. In Google Cloud Console, choose your project and enable the Google Drive API.
  2. Configure the Google Auth Platform consent screen. While it is in Testing, add the Google accounts you will use as test users.
  3. Create a Web application OAuth client for local development. A Chrome Extension client is not the right type for this launchWebAuthFlow implementation.
  4. Load the unpacked extension in regular Chrome and copy its ID from chrome://extensions/.
  5. Register https://<DEV_EXTENSION_ID>.chromiumapp.org/ as an authorized redirect URI, including the trailing slash.
  6. Put that client ID in VITE_GOOGLE_DRIVE_CLIENT_ID in .env.development, then restart WXT.
  7. Create a separate production Web application client using the published extension ID and put its client ID in .env.production.
  8. Test Connect Google Drive in the regular Chrome extension. Before public use, complete Google’s consent-screen publishing and any applicable review requirements.

The requested scope is drive.appdata. Backups live in the app-data area, not as normal files listed in My Drive. Do not put an OAuth client secret into the extension.

Preview UI without real providers

pnpm dev:preview

This serves the actual options UI at http://127.0.0.1:4173/ with sample data. It disables environment-file loading and real Gemini and Drive calls. Sample profile edits reset on refresh; the base preview remembers appearance. It does not replace extension-browser checks for scanning, writing, OAuth or popup behavior.

Follow the request

From the page to a saved decision

A popup or Quick Fill request is handed to the background coordinator. The coordinator owns run state and sends work to the content scripts in the captured tab and frames. Closing the popup does not cancel an accepted run.

Area Start here Responsibility
Entrypoints entrypoints/ Background worker, content script, popup and options UI.
Run coordination src/autofill/runCoordinator.ts Per-tab runs, pending choices, interruptions and recovery.
Scan → match → write src/autofill/ Eligible controls, learned/rule matching, AI handoff, verified writes, Undo and learning.
Field catalog src/profile/fieldCatalog.ts Shared labels, layout order, input IDs, aliases and mapping paths. Metadata and policies feed review, completion, projections and disclosure.
Profile schema src/types/profile.ts Canonical data. Validators, normalization and migrations still need explicit handling when fields change.
AI requests src/resume-ai/ Gemini calls, prompts, extraction, validation and import comparison.
Backup src/utils/driveSync.ts OAuth, conditional writes, backup review and retries.
Fill reports src/fill-log/ Frame aggregation, metadata retention, presentation and navigation.

Keep the shared contracts intact

New profile fields need catalog entries, typed UI bindings, domain validation, import/export policies and migration decisions. The catalog reduces duplicate definitions; it does not make a schema change automatically safe.

Do not put Gemini credentials or Drive tokens into profile exports. AI requests use a known-field projection and question-scoped sensitive data. Preserve the two-phase scan/fill behavior and the manual-learning confirmation rules.

For the detailed architecture and project conventions, read AGENTS.md. This site is the user and developer guide; code remains the source of truth for implementation details.

Everyday development

Run the check that answers the question

Command Purpose
pnpm dev Run WXT Chrome development with live updates.
pnpm dev:preview Run isolated sample-data options UI at port 4173.
pnpm compile Type-check without emitting files.
pnpm lint Run ESLint.
pnpm test / pnpm test:run Vitest in watch mode / a single run.
pnpm build Build production Chrome output in .output/chrome-mv3/.
pnpm zip Build and package a Chrome Web Store archive in .output/.
pnpm test:browser Build, then run Playwright extension tests.
pnpm serve:landing Serve this static website from docs/.
pnpm dev:firefox, pnpm build:firefox, pnpm zip:firefox Firefox development, build and package scripts. Production distribution targets Chrome.
pnpm format / pnpm lint:fix Formatting and automatic lint fixes. Scope edits to the work you intend to change.

Before sharing a change

pnpm compile
pnpm lint
pnpm test:run
pnpm build

CI runs the same four checks on branch pushes and pull requests. Use focused existing tests while working, for example: 

pnpm exec vitest run src/autofill/mapper.test.ts

Vitest defaults to Node. DOM tests opt in with // @vitest-environment jsdom. Keep tests under src/, outside WXT’s entrypoints.

Check actual form behavior

pnpm exec playwright install chromium
pnpm test:browser
# After a build, inspect a run in a visible browser:
pnpm exec playwright test --headed

Autofill-matching changes need browser verification as well as unit tests. Check retained values, validation, events and Undo on a throwaway form. Browser tests use isolated Chromium storage and synthetic data, not your installed extension’s personal profile.

A form you can test freely

An original application for a fictional role

The Morrow Studio demo is a standalone job application made for this project. Its layout and branding are original, rather than a reproduction of an ATS. It does not send applications or save form entries. You can use it for manual autofill checks and public screenshots.

The page itself has no Job Buddy links, sample-profile download or testing tools. The floating control comes from the installed extension. Use synthetic profile information for screenshots; do not publish your actual resume or credentials.

Location Purpose
docs/demo/ Buildless HTML, CSS and local form behavior.
src/browser/fixtures/demo-profile.json Internal fictional profile used by browser checks and captures.
src/browser/demo.pw.ts Real extension fill, validation, events and Undo checks.
src/browser/site-captures.pw.ts Reproducible light/dark website captures of the real UI, with isolated sample data and mocked providers.
docs/assets/screenshots/ Reviewed 3× lossless website screenshots. Regenerate when the UI changes. 
pnpm build
node scripts/capture-demo.mjs
node scripts/capture-site.mjs

For website captures, keep pnpm dev:preview running at port 4173 in another terminal. They are opt-in and skipped during ordinary browser tests. Capture output is written under .output/browser-results/. The scripts update the image assets and cache versions; website conversion requires cwebp. Review the results before committing. Keep HTML image dimensions in CSS pixels, not the 3× bitmap dimensions. The website and README use the same current demo rather than older ATS screenshots.

For maintainers

Configure releases separately from development

The release workflow runs when a v*.*.* tag is pushed. It checks, builds and zips the extension, uploads it to Chrome Web Store and creates a GitHub release. This is a publishing action, not a local test command. Store approval and Chrome’s rollout are separate from the upload.

Prepare the publishing credentials

  1. In the Google Cloud project that owns publishing access, enable the Chrome Web Store API.
  2. For the CLI helper below, create a Desktop app OAuth client following its setup guide. This is separate from the Web application clients used for Drive.
  3. Find the extension ID in the Chrome Web Store Developer Dashboard.
  4. Generate publishing credentials using the maintained chrome-webstore-upload-keys utility and the account that owns the listing. Keep the resulting tokens private.
  5. Create a GitHub environment named production and add the secrets below.
Secret Value
CHROME_EXTENSION_ID The published extension’s ID.
CHROME_CLIENT_ID The publishing Desktop app OAuth client ID.
CHROME_CLIENT_SECRET That publishing client’s secret.
CHROME_REFRESH_TOKEN A refresh token authorized by the listing owner. Reauthorization is needed if it is revoked or expires.
ENV_PRODUCTION Production environment-file text containing VITE_GOOGLE_DRIVE_CLIENT_ID=<PRODUCTION_DRIVE_CLIENT_ID>. Use the Drive Web application client ID, not its secret.

See release.yml for the exact upload steps. Keep release approval, version choice and tag publication explicit.
