Requirements

Install these tools to build and run Job Buddy on your device.

Tool Minimum or required version Purpose
Node.js  22.13.0 or newer within Node 22 Runs the development server, build tools and tests.
pnpm  11.7.0, pinned by the project Installs dependencies and runs project commands.
Git  No minimum specified Clones the repository and tracks code changes.
Google Chrome  No minimum specified Loads the extension and tests autofill on job forms.

Set up the project

Clone the repository, install its dependencies and start the development build.

git clone https://github.com/myowinthein/job-buddy.git
cd job-buddy
pnpm install
pnpm dev

pnpm dev opens a new Chrome window and loads the development extension with an amber Job Buddy logo. The localhost address printed in the terminal belongs to WXT’s development server.

Can I use my regular Chrome profile?

Yes. This is useful for testing real Google sign-in, which may be restricted in the browser opened by WXT.

  1. Keep pnpm dev running.
  2. Open chrome://extensions/ and turn on Developer mode.
  3. Click Load unpacked and choose .output/chrome-mv3-dev/.
  4. The amber development extension stores data separately from the blue live version.
When should I reload the extension or refresh a form?

Keep pnpm dev running while you edit. The action depends on what changed.

  • Popup or options page changes usually appear automatically. If they do not, reopen the popup or refresh the options page.
  • Autofill or content script changes need a fresh copy on the job form. Open chrome://extensions/, find the amber Job Buddy development extension and click Reload. Then refresh the job form.
  • A new HTML entrypoint needs a server restart. Press Ctrl+C in the terminal running pnpm dev, then run pnpm dev again. Reload the development extension afterward.

Environment files

Copy .env.example to .env.development for local testing, then set the values you need.

VariableUse
VITE_GOOGLE_DRIVE_CLIENT_ID Enables Google Drive backups through this build’s shared OAuth client ID.
VITE_GEMINI_API_KEY Optionally preloads your Gemini key for local development.

Restart pnpm dev after editing an env file to load the updated values.

How do I configure Google Drive OAuth?
  1. Enable Drive
    • In Google Cloud Console , select your project.
    • Under APIs & Services, open Library, find Google Drive API and click Enable if needed.
  2. Configure consent
    • Open APIs & Services, then OAuth consent screen to reach Google Auth Platform.
    • If prompted, click Get Started, enter the app name, support email and contact email, and choose External for personal Google accounts.
    • Under Audience, if Publishing status is Testing, use Test users and Add users to add your test accounts, then click Save.
    • Under Data Access, click Add or remove scopes, select https://www.googleapis.com/auth/drive.appdata, then click Update and Save.
  3. Create the OAuth client
    • Load the amber development extension and copy its ID from chrome://extensions/.
    • In Google Auth Platform’s Clients, click Create client, choose Web application as the Application type and name it Job Buddy development.
    • Under Authorized redirect URIs, click Add URI and enter https://<DEV_EXTENSION_ID>.chromiumapp.org/ using the copied ID, including the trailing slash. Click Create.
  4. Test locally
    • Set VITE_GOOGLE_DRIVE_CLIENT_ID in .env.development to the new client’s Client ID.
    • Restart pnpm dev and reload the development extension.
    • In Job Buddy’s Settings, click Connect Google Drive under Cloud Backup.
  5. Prepare for public use
    • Create a separate Web application client with the published extension’s redirect URI.
    • Copy .env.example to .env.production and set VITE_GOOGLE_DRIVE_CLIENT_ID to this client’s ID.
    • In Audience, click Publish app under Publishing status. Confirm it shows In production.
    • Complete any checks requested in Verification Center.

Backups use the Drive app-data area with the drive.appdata scope. They are hidden from My Drive.

See Google’s OAuth setup guide, Web application client instructions and publishing settings for more detail.

Use the dev bar

Switch profile and integration states from the bar at the top of the development options page. It is hidden in production.

Sample profiles run in an isolated view and reset on refresh. Original returns to your saved data. Integration toggles keep temporary edits and simulate Gemini and Drive without calling either provider.

Does this change the popup or forms I am testing?

No. The bar simulates the options page only. Use the unpacked extension to check real autofill, the toolbar popup and Google sign-in. The unsaved-changes guard still applies when switching profile modes.

Can I preview the UI without loading an extension? 
pnpm dev:preview

Open http://127.0.0.1:4173/ for the options UI with sample data. Environment files and real provider calls are disabled. Profile edits reset on refresh. The base preview remembers appearance, while dev-bar simulations reset it.

Follow the code

Clicking Fill Form hands the request to the background coordinator. It tracks the run and directs content scripts in the source tab and frames. Once the request is accepted, closing the popup does not stop it.

  1. Scan

    Find eligible controls and their questions across frames and open shadow roots.

  2. Match

    Try learned mappings, rules, then AI for fields that still need help.

  3. Write

    Apply answers, verify retained values and keep snapshots for Undo.

Corrections can teach future runs. Fill Details follows the current run and later edits, keeping one metadata-only report rather than an application history.

Stack and storage

WXT builds the Manifest V3 extension. React 19, TypeScript 5.9 and Tailwind CSS v4 power the UI. Vitest covers domain behavior and Playwright checks browser interactions. Profiles live in chrome.storage.local. Run coordination and the retained fill report use session storage.

Working onStart here
Extension surfacesentrypoints/ for the worker, content script, popup and options UI.
Autofill runssrc/autofill/runCoordinator.ts for run state, choices and recovery.
Scanning, matching and writingsrc/autofill/ for the scanner, mapper, resolver, filler, Undo and learning.
Profile fieldssrc/profile/fieldCatalog.ts for shared labels and order. src/types/profile.ts for the schema.
Gemini and resume importsrc/resume-ai/ for requests, prompts, validation and comparison.
Backupssrc/utils/driveSync.ts for OAuth, writes, restore review and retries.
Fill reportssrc/fill-log/ for aggregation, retention and navigation.
What needs updating when I add a profile field?

Add its schema and catalog entries, UI binding, validation, import/export policies and migration handling. Check completion, extraction and AI disclosure rules. The catalog shares definitions across features, but does not replace these decisions.

Run src/profile/fieldCoverage.test.ts to check coverage across profile projections, review, extraction and prompts.

Which autofill and data rules should changes preserve?
  • Scan once, then use the saved matches for merge or overwrite.
  • Verify writes and preserve Undo when a form rejects a value.
  • Learn from confirmed manual corrections, never AI confidence alone.
  • Keep Gemini credentials and Drive tokens out of profile exports and backups.
  • Limit AI requests to permitted profile fields and question-specific sensitive data.

Release setup

Pushing a version tag such as v1.14.4 starts GitHub Actions. It checks the code, builds the extension, uploads a Chrome Web Store draft and creates a GitHub release.

Add these secrets to the repository’s production environment.

SecretPurposeWhere to get it
CHROME_EXTENSION_ID Identifies the store listing to update The item ID in Chrome Web Store Developer Dashboard 
CHROME_CLIENT_ID Identifies the OAuth client used for uploads Get the publishing client ID
CHROME_CLIENT_SECRET Authenticates that publishing client Get the publishing client secret
CHROME_REFRESH_TOKEN Authorizes uploads using the listing owner’s account Generate the refresh token
ENV_PRODUCTION Supplies production build settings The contents of .env.production, including the production Drive client ID

Review the draft in Chrome Web Store Developer Dashboard  and click Submit for Review. Submission is intentionally manual, though the upload tool can automate it.

How do I get the Chrome Web Store upload credentials?
  1. Prepare the project
    • In Google Cloud Console , select the project used for publishing.
    • Under APIs & Services, open Library, find Chrome Web Store API and click Enable if needed.
    • If Google Auth Platform needs setup, follow the app-details and test-user steps in the OAuth setup instructions above.
  2. Create the publishing client
    • In Google Auth Platform, open Clients and click Create client. Set Application type to Desktop app, name it Job Buddy uploads and click Create.
    • Save Client ID as CHROME_CLIENT_ID and Client secret as CHROME_CLIENT_SECRET before closing the creation dialog. Google shows the full secret only once.
    • For an existing client, find Client ID under Additional information. Use your saved secret, or click Add client secret and save the newly generated value.
  3. Generate the refresh token
    • Run the credential helper in your terminal. 
      npx chrome-webstore-upload-keys
    • Enter the saved values at the Client ID and Client secret prompts, then choose to open the authentication page in your browser.
    • Sign in with the Google account that owns the store listing and approve the requested Chrome Web Store access.
    • When the helper finishes, save the printed REFRESH_TOKEN value as CHROME_REFRESH_TOKEN.
  4. Save the GitHub secrets
    • In the GitHub repository, open Settings, then Environments. Open production, or create it with New environment and Configure environment.
    • Under Environment secrets, use Add secret to save each name and value from the table above.

See Google’s OAuth client guidance, the credential helper guide and GitHub environment setup for more detail.
